# Issue #161: Precedent wakes the sleeping legal engine on every health check

- State: closed (2026-11-01)
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/arize-ai-hackersprint/issues/161

The legal engine on the VPS (4.6 GB in memory) now sleeps when nobody uses it. `legal-engine.socket` holds 127.0.0.1:8011 and starts the engine on the first connection, which takes about 75 seconds; after 20 minutes with no connection the engine stops again (Pukujan-lab/server-management#80).

Precedent keeps it awake. Every hit on `/api/health` and `/api/stack` calls `engine.status()`, which sends GET `/api/v1/health` to the engine. Deploy health checks, the red-team workflow every 6 hours and every page load (the frontend reads `/api/stack` to decide live vs sample) add up to roughly 80 wakes a day.

A second problem shows up once the engine can sleep. When the engine errors, `app/octo_retriever.py` falls back to Octo SQL or the local snapshot and caches that answer with no expiry, so the same question never reaches the engine again.

What we will change:

1. `/api/health` and `/api/stack` report the engine from `systemctl is-active legal-engine.service` (active means ready, inactive means asleep and wakes on request), cached for a few seconds, with no connection to the engine. The JSON shape stays the same.
2. A new `POST /api/engine/warm` opens one background connection to the engine. It runs at most once every 5 minutes across all visitors and is rate-limited per IP. The frontend calls it once on page load and on first focus of the question box, and never again from an idle tab.
3. Fallback retrievals expire from the cache after 10 minutes. Engine results stay cached as today. When the engine times out or cannot be reached, the run says the engine is waking up and to ask again in a minute or two.

Done when the PR is merged and deployed, and `journalctl` on the VPS shows no engine start caused by `/api/health` or `/api/stack`.
