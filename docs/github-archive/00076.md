#74 asked PRs to say which OSS they considered, but nothing checked it. This PR makes the gates job check it, and adds checks for new dependencies.

## What the gates job now checks

1. PR body (tools/pr_policy.py, glue around `gh`). A PR that adds a source file, or more than 150 non-test lines, under app/, acs/ or tools/ fails unless the body has an "OSS considered" section that names a specific project or SDK and why it does not fit. A bugfix can skip that with the `bugfix` label or a `Bugfix:` line, as long as it closes an issue with confirmed evidence. Docs, tests, static/ and CI-only PRs pass without either. New raw `httpx` or `requests` calls to providers that ship an SDK get a warning, not a failure. The check reruns when the body or labels change.
2. The lock. requirements.in now holds the direct dependencies, and requirements.txt is the `uv pip compile` lock. Its Python 3.9 branch pins exactly what the Pro's venv runs today (I checked all 47 packages), so the deploy's `pip install` changes nothing there. The 3.10+ branch pins the versions CI installs today. CI recompiles the lock and fails if it differs.
3. Licenses. pip-licenses reads every locked package, and anything outside MIT, BSD, Apache, ISC, PSF, MPL-2.0, Unlicense, 0BSD, Zlib or CC0 fails, including GPL-family and unknown licenses.
4. Vulnerabilities. pip-audit checks the pins CI installs. It fails when the PR changes the requirements and only warns otherwise. A second run reports the Pro's 3.9 pins as a warning.
5. Maturity. Each new direct dependency needs a PyPI release within the last 12 months.
6. Dependabot opens weekly pip and GitHub Actions PRs, and they go through all of the above.

actions/dependency-review-action with OpenSSF Scorecard is wired in but stays off for now. The repo's dependency graph is off, and the action fails without it. Turning on the dependency graph in Settings and setting the repo variable `DEPENDENCY_REVIEW` to `on` enables it.

## Something the audit found

The Pro runs Python 3.9, and its current pins have known advisories in starlette 0.49.3, python-multipart 0.0.20, urllib3 2.6.3, requests 2.32.5, anyio 4.12.1 and python-dotenv 1.2.1. The fixed releases need Python 3.10 or newer, so the real fix is moving the Pro off 3.9, which #20 already tracks. This PR leaves the Pro's versions alone and reports them as a warning. Part 2 of #20 (pinning) is covered by the lock here. #20 stays open for the Python move and the contract test on the Pro.

## Docs and templates

AGENTS.md now spells out the rule, the bugfix route, SDKs over raw HTTP, and the lock workflow. contracts/agents/coding-agent.json picks up the same rules and may write requirements.in. The PR template's OSS section explains what counts. A new `.github/PULL_REQUEST_TEMPLATE/aba.md` comes with the section filled in, so ABA PRs pass as written (`gh pr create --template aba.md`). repo.manifest.json lists requirements.in.

## Tests

tests/test_pr_policy.py runs 17 fixture PRs from tests/fixtures/pr_policy_cases.json: exempt docs, tests and frontend PRs; new modules with no section, the untouched template, "no new module", or a vague line; named OSS with a reason; bugfix with and without a confirmed issue; the 150-line edge; and the SDK warning. It also checks that the default template fails as is and the ABA template passes. tests/test_dep_policy.py covers marker-aware pins, new direct dependencies, release age including yanked and missing packages, the license allowlist, and that the lock pins every direct dependency. The OIO and CGM validators pass locally. Dry runs against #74, #72, #68, #65 and #60 all come out exempt.

## OSS considered

- `danger/danger-js` (and `danger-python`): could run the PR-body rule, but it needs Node plus a Dangerfile and a bot token setup, which is more moving parts than about 100 lines of glue around `gh`.
- `actions/dependency-review-action`: covers licenses and vulnerabilities for changed dependencies, but it needs the dependency graph, which is off here. It is wired in behind a variable, and pip-audit and pip-licenses cover the same ground in the meantime.
- `ossf/scorecard-action`: scores this repo, not the packages it depends on, so the maturity rule uses PyPI release dates instead.
