### Affected App, Adopter, Users, or Systems

Every PR to this repo, coding agents and ABA runs, and the Pro deploy that installs requirements.txt.

### Observed Consequence and Workaround

Observed: #74 asks a PR that adds a custom module to say which OSS options were considered, but nothing checks it. A PR can add a new module under app/ with an empty "OSS considered" section and still merge. New dependencies get no license, vulnerability or maturity check, requirements.txt has no version pins (see #20), and there is no Dependabot config. Nothing says to prefer a provider's official SDK over raw HTTP calls.
Expected: the gates job fails a PR that adds a new source module, or more than about 150 non-test lines under app/, acs/ or tools/, unless the body names a specific OSS project or SDK and why it does not fit, or the PR is a labeled bugfix linked to an issue with confirmed evidence. Docs, tests and CI-only PRs pass untouched. New dependencies pass a license allowlist, a vulnerability scan and a release-age check. Versions are pinned in a lock file and Dependabot keeps them current.
Workaround: Alex reviews each PR by hand.
