`capture` was the only part of the pipeline with no test. It calls `app.engine.retrieve`, so a renamed config key or a changed result shape would have surfaced only in a live run against the engine — which needs credentials the test suite does not have.

Three tests with a fake `retrieve` now pin:

- **The request** — the exact config dict the engine receives (`k`, `bm25_k`, `dense`, `dense_pool`, `graph`, `graph_seed_docs`, `rerank`, `rerank_k`, `jev`).
- **The artifact** — format, `run_id` shape, config echo, `corpus_revisions`, `capture_complete`, and the graph counters.
- **Two failure paths** — an engine exception and a response that breaks the contract both land in the record without losing the artifact.

I checked the assertions have teeth: mutating `bm25_k` from 100 to 50 fails the request test. A first mutation of `rerank_k` did *not* fail, because the test passes `rerank_k=30` and the mutation hardcoded 30 — a good reminder that a passing mutation check only proves what it covers.

The tests use a plain temp directory rather than pytest's `tmp_path`, because this sandbox blocks `mkdir` of the pytest temp root and would otherwise fail them for an unrelated reason.

Verification: `ruff check` and `ruff format --check` pass; 42 tests pass in `tests/test_retrieval_eval.py` (39 before, 3 added).
