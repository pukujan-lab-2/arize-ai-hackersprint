## Summary
- Retrieval calls the retrieval engine on the same host (dense + rerank + graph + checker); the engine's result list is the candidate set, with the Octo fallbacks kept for when the engine is down.
- Every run records the retrieval stages it actually took; the citation map, the follow-ups and the observability page read the new fields.
- Tracing reports the exporter's own verdict with sent/dropped/queued counts, and both the saved-run store and the trace queue are bounded first-in-first-out with caps the page states.
- The observability page restores the v1 Arize hookup: the judge-score snapshot (`arize/observability-snapshot.json`) served at `GET /api/arize`, merged with live runs, a span waterfall per trace, and an honest "unavailable" state.
- Greeting questions (a bare "hello") get a refusal with no citations instead of incidental testimony; the citation check is not reported as passed in that case.

## OSS considered
- `httpx` — not used: the app already depends on the standard library and `requests` is not installed on the Python 3.9 host, so a small `urllib.request` client in `app/engine.py` avoids a new runtime dependency; the client is one POST/GET wrapper, not a transport layer.
- `cachetools` — not used: the engine health cache is a single 10-second timestamp, which does not justify a new dependency.
- `aiolru` / `p-queue` — not used: the run store and trace queue need oldest-first eviction with counters the page can report, and neither package reports what it drops.
