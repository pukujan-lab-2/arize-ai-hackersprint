# PR #171: Test whether fixing the graph merge would help (it would not)

- State: open
- Opened by Pukujan on 2026-11-01
- Original: https://github.com/Pukujan-lab/arize-ai-hackersprint/pull/171
- Branch `workbuddy/graph-merge-experiment` into `main`, +100 −0 in 2 files

The graph merge order does suppress the graph: neighbours score 0.0 in the fusion and are cut before `k`. This tests whether fixing that would actually improve retrieval.

An env-gated `GRAPH_SLOTS` was added to a **second engine instance on port 8013** — production was never restarted and the deployed code is unchanged — and 20 development questions were captured with slots on and off.

**It works mechanically:** 5 of 20 queries change, exactly the five with graph additions.

**It does not help.** What arrives is citation proximity, not relevance. For *"What did the court decide about the property issue?"*, the hybrid head ends on a tax case, and the graph then contributes:

```
11  Helvering v. Grinnell
12  Griffiths v. Commissioner
13  Abbott Laboratories v. Gardner
14  Keystone Bituminous Coal Ass'n
15  Lucas v. South Carolina Coastal Council
```

Abbott is administrative procedure, Helvering/Griffiths are tax. They arrive because the graph followed citation edges out of a tax case that mentioned property. Lucas and Keystone are real takings cases, so some of it may be useful — and nothing in this experiment separates the useful from the noise.

**Conclusion:** the merge order is necessary but not sufficient. One-hop expansion has no relevance gate, so a neighbour of a highly-ranked case is admitted regardless of whether it answers the question. A useful graph contribution needs a scoring signal or a gate on what enters — a bigger change than moving items in a list.

The engine is at its baseline commit (`a72024b`), `GRAPH_SLOTS` does not exist in deployed code, and ranking behaviour is unchanged.
