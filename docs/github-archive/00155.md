Adds an offline evaluation harness for retrieval, plus the question set and the guide that govern it. Claimed as HACK-04 (retrieval improvement for case law).

## What it does

`tools/retrieval_eval.py` captures engine candidates through `app.engine`, pools two arms into a blinded union, exports a review sheet, builds qrels from it, scores nDCG@10 / precision@3 / precision@10 / recall of known relevant documents, and reports paired bootstrap intervals between arms.

Four properties are enforced rather than assumed:

- Metrics are withheld until every pooled candidate carries a 0/1/2 judgment, so a partial sheet produces no numbers instead of optimistic ones.
- `--for-selection` refuses any split but `development`.
- `pool` refuses captures spanning more than one corpus or graph revision, because a corpus that moved between arms is not a ranking difference.
- Graph-only candidates come from the graph stage's `added[]`, not from `provenance`: real result rows only ever name `bm25` and `dense`.

## What the development split showed

Twenty development queries against the live engine, graph on and graph off, identical result lists on all twenty, at `k=50` with reranking both off and on at `rerank_k=30`. Twenty-five graph additions across five queries, none of which reached the result list.

The reason is in `pipeline.py`, not in the graph: neighbours are appended to `pool` but never enter `fused`, so `final_score` gives them `0.0` and they sort below every hybrid candidate; reranking only rewrites `ranked[:rerank_k]`, and the response is then cut to `k`. This PR does not change that. It measures it and records it.

## OSS considered

- `ir_measures` (https://github.com/allenai/ir_measures): scores nDCG and recall from qrels, but it takes rankings as input and has no notion of capturing from the engine, pooling two arms into a blinded union, or attributing a candidate to the graph stage. Adopting it would still leave all of that to write, so it does not replace this tool.
- `ranx` (pypi:ranx): the same split between scoring and capture, with a heavier dependency set than four metric functions need here.
- `pytrec_eval`: requires a C extension build for nDCG@10 and recall, which is more than this repo's stdlib-only tooling warrants.
