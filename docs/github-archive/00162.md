# PR #162: Let the legal engine sleep when nobody is using Precedent

The legal engine on the VPS now sleeps when idle and starts on the first connection to 127.0.0.1:8011, which takes about 75 seconds. Until now Precedent woke it about 80 times a day, because `/api/health` and `/api/stack` sent a health request to the engine on every hit. This PR stops that and adds a deliberate wake-up when someone opens the site.

Closes #161

What changes:

1. Status reads ask systemd. `engine.status()` runs `systemctl show legal-engine.service` and maps `active` to ready, `activating` to waking and `inactive` to asleep, cached for 5 seconds. It opens no connection to the engine. The detail fields (chunk count, models) come from the last health answer the engine gave a warm-up. On a host where systemd does not manage the engine, status still probes the engine as before. The JSON shape is unchanged.
2. `POST /api/engine/warm` starts one background GET of the engine's health (120 s timeout). It runs at most once every 5 minutes for the whole process and allows 4 calls per minute per IP. The chat page calls it once on load and once on the first focus of the question box. An idle tab sends nothing more.
3. Fallback answers expire. When the engine fails and retrieval falls back to Octo SQL or the snapshot, that result now stays in the local cache for 10 minutes and is no longer written to the shared Octo `retrieval` table. Old fallback rows already in Octo are ignored on read. Engine results stay cached as before.
4. When the engine times out or cannot be reached, the run records `waking: true` with a plain reason, and the answer shows a note that the full search is waking up (about 1–2 minutes) and to ask again shortly.

Tests: `tests/test_engine_sleep.py` covers each case. The status test fails if any engine connection is attempted. Ruff, mypy, the full pytest suite and the frontend build pass locally.

## OSS considered

`pystemd` (`systemd/pystemd`) could read the unit's state over D-Bus. It needs libsystemd headers to build and is one more dependency for a single property read, so we call `systemctl show` through `subprocess` instead. `cachetools` (`tkem/cachetools`) offers TTL caches, but the module already caches the engine's health with a timestamp and a lock, and the new caches follow that pattern in a few lines.
