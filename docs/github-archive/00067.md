### Observed Consequence and Workaround

Observed: tests/test_memo_then_tour.py::test_slow_memo_is_not_dropped_at_8s fails on main (7cacafd). With the TTS reply held back 12 s, the memo clip starts playing (currentTime reaches 0.064 s of a 1 s clip) and then stops advancing: it never pauses, never ends, and AudioMgr.say() never resolves, so the status stays on 'Audio loading…' and anything queued behind the memo, such as the tour, waits forever. It fails the same way with static/audio.js as of #21 (fcb36b2), so it is not a regression from #59 or #65.
Expected: A slow memo still plays to its end and say() resolves, then queued narration continues. A clip that truly stalls must not block the queue forever: it is resumed, or skipped with a visible status, never left hanging. The 8 s rule for tour stops stays.

**Pukujan commented, 2026-10-17**

Root cause: the test browser, not the page. Headless Chromium on the Mac host freezes a clip's clock at 0.064 s even with none of our code loaded, so the clip never ends. Adding `--disable-audio-output` to the shared test browser flags fixes it, and every audio test passes against main's audio.js unchanged. ABA's attempt (a watchdog that jumps stuck clips to their end) only hid the stall, so it was not shipped.
